# Database Migration Register

Migrations live in `backend/drizzle/` and are generated by drizzle-kit from `backend/src/database/schema.ts`. They are applied automatically when the API starts (`bootstrap.ts`; the Docker image runs `dist/database/migrate.js` first), or manually with `npm run db:migrate`. Each file runs once and is recorded in `drizzle.__drizzle_migrations`.

All migrations added in this work are **additive**. They add types, tables, columns and indexes. No column or table is dropped or renamed, and no row is deleted. Test them on a copy of production (a Neon branch) before deploying.

| # | File | Change | Data handling | Rollback |
|---|---|---|---|---|
| 0000–0005 | `0000_init` … `0005_questions_bank_columns` | Existing schema (before this work) | — | — |
| 0006 | `0006_attempt_integrity_and_revisions.sql` | Enum value `attempt_status.auto_submitted`. Table `question_revisions` (unique `question_id, version`). Columns: `questions.version` (default 1), `test_answers.version`, `saved_at`, `correct_option_snapshot`, `question_version`, `test_attempts.last_saved_at`. Partial unique index `test_attempts_one_open_uq` | Before the index, **duplicate open attempts** for the same user and test are closed: the newest stays open, older ones become `submitted`, late, score 0, max score from the test (nothing deleted). Open attempts get their answer-key snapshot backfilled | Drop the new index, table and columns. The enum value cannot be removed in PostgreSQL; it is harmless if unused |
| 0007 | `0007_guest_abuse_protection.sql` | Table `abuse_events`. Columns `device_hash`, `network_hash` on `users` and `test_attempts`, with indexes | None (new columns are NULL for old rows; old guests are simply not grouped) | Drop the table, columns and indexes |
| 0008 | `0008_user_progress.sql` | Tables `user_bookmarks`, `user_mistakes`, `user_progress`, `progress_events` (all keyed by user, cascade on user delete) | None. Existing browser progress is uploaded once by the website on first sync | Drop the four tables |

## Settings stored in `app_settings` (no migration needed)

| Key | Content |
|---|---|
| `access_policy` | Guest free-quota policy (see [SecurityAudit.md](SecurityAudit.md)); defaults apply when absent |
| `abuse_hash_secret` | Random HMAC key, created on first use when `ABUSE_HASH_SECRET` is not set |

## Verification

Migrations ran from an empty database on PostgreSQL 16 and on PGlite in every test run (197 tests each). Migration 0006's duplicate-closing step was not tested against a database that actually contained duplicate open attempts; production data is expected to contain few or none.

## Deployment order

1. Deploy the API (applies 0006–0008 on start).
2. Deploy the website and admin straight after.

From step 1 on, the API withholds the paper from anonymous requests. An old website build would fail to open live tests until step 2, so deploy both together.
